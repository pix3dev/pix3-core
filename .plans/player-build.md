## Deviations from the plan

- §B.6 item 2 «importer protection»: P1 ships the table's own fixpoint (`importers`, `lazyValueImporters`) and the dependency rule; `this.parse` of dependencies' named imports is P2 (as the item itself says).
- §B.6 item 5 classic rewrite: extended beyond DeepCore's (`import.meta.resolve`, generic `import.meta`), see P9.
- `postprocessing` stub needed its own pre-plugin (P8) — the 1.x alias map had no such ordering problem.
- The player's scene list is constant-folded out of a build whose entry is known (rolldown); the spec judges the entry by `.pix3/build.json`, not by grepping the bundle.
- §B.6 item 4 (B.6.4): done as JSON scenes + a per-importer `yaml` stub (P20), not as the `parseSceneText`/`buildGraph` split with `virtual:pix3/scene-documents`. Same gate, no runtime API change at all (§H item 5 «B.6.4 только добавляет» holds trivially).
- §G.3 «Export UI»: none — owner decision 2026-10-10 (P12).
- `dist/<name>.report.json`: `<name>` is the artifact's basename (`index` for html), not the project name, so the report pairs with the file it describes.

## Debt

- WebP re-encoding of embedded images (optional `sharp`), `export.{prune,include,exclude}Globs` — P2+ as the plan says; neither is asked for by a starter.
- N11 pre-scan reads direct dependencies only (`runtimeDependents`); a transitive dependency that imports the runtime is caught by the `transform` net, which fails the build with the fix rather than keeping the module itself (it runs after the runtime's modules are loaded and stubbed). A `strip.keep` names the classes; good enough until a real library shows the pattern.
- The report's per-group bytes are rendered (pre-minify) lengths from the bundler plus a scaled estimate; exact minified attribution would need a source map pass.
- The `yaml` stub rides on `strip`: `strip: false` ships the parser and YAML scenes. A project that wants the stubs but no node stripping has no switch (none asked).
- The build specs run under the checkout's Vite 8 only; Vite 7 is exercised by the harness (`--vite 7`, P22), which must be re-run after a plugin change that touches the build hooks.
- The 1.x `vite-plugin-singlefile` `removeViteModuleLoader` is off (P17); if a future Vite emits a preload polyfill despite `modulePreload: false`, the classic page would carry it inert.
