### Threat model — Remote SSH (A20–A23)

| | |
|---|---|
| Protected | The human's Chrome: CDP is full control of the Pix3 profile and, through navigation, `file://` reads on the human's machine. The token is the key to it. |
| Adversary | Another user of the remote host (shared loopback, world-readable `/proc/*/cmdline`, perhaps a readable project folder); a web page in the human's browser (A16's Origin/Host checks, unchanged). |
| Holds | The forwarded port answers nobody without the token (401, before an upgrade). On the remote host the token is only in `~/.pix3/remote-cdp-token` and `~/.pix3/remote-cdp.json`, both 0600 (the copy runs under `umask 077`; a wider file is narrowed on read) — not in the project, not on any command line, not in any output. `pix3`'s probes never send it to a port that has not proven it knows it (A23). |
| Residual | (1) **A squatter on the forward port**: another user binds R before the session; with `ExitOnForwardFailure yes` the SSH connection fails visibly and the agent has nothing to connect to; without it, or while the session is down and the agent reconnects, chrome-devtools-mcp sends the token to whoever holds R (it cannot ask for the proof). The stolen token is usable only through a later forward of the same proxy → if a forward ever failed to bind, rotate the token. (2) The user's own account and root on the remote host can read the token (the same boundary as A16 locally). (3) **Not ours to fix here**: the remote dev server (`/__pix3/api/*` reads and writes the project) answers any user of the remote host on its loopback, as any Vite dev server does; the plugin's guard checks loopback, not the user. |
