## 2. Decisions

| # | Decision | Why |
|---|---|---|
| S1 | The contract-B scan is **lexical**, in the CLI, with no parser and no TypeScript. | `check` must run where TS is not installed yet; the three constructs are lexically unambiguous once comments and string text are masked. A dynamic import is literal only when the argument is one string (or a template without `${}`) followed by `)` or `,` — what Vite's `es-module-lexer` sees as a specifier; anything else gets `__vite__injectQuery`. |
| S2 | The scan follows local specifiers only (relative, `/`-rooted), not bare packages or tsconfig `paths`. | A package's code is not the project's to fix; aliases are rare in game scripts. Recorded as debt. |
| S3 | Warnings, not errors. | The game still builds and runs; only the editor tab is at risk (a `full-reload` reaches it). The page alarm makes a miss visible at runtime. |
| S4 | Bot policies are applied during play; everything else (including a helper outside `design/tests/bots/` a policy imports) still waits for play to stop. | A policy is test code the next `pix3_game_run` reads from the roots — nothing to restart. A helper outside the folder may be the game's too; the page cannot tell, so it stays conservative (debt). |
| S5 | A sync acknowledges only entries reported **before** the plugin asked the tab (`reportMark`). | Frames of the rescan precede the request on the same socket and are handled synchronously; a newer write's frame comes after and must not be dropped. |
| S9 | **A sync applies and acknowledges every entry reported before the plugin asked, not only its own rescan's `changed`** (`SyncApplyService.apply`: `changed ∪ ExternalChangeService.reportedUpTo(mark)` → `ExternalReloadService.apply` → `acknowledge`; an entry whose version does not parse keeps its "last good graph" path). Extends S5. | The plugin's watcher broadcasts a settled write on its own (`ProjectFiles.flushDirty`, ~`stabilityMs` after the write). A sync that comes after that frame finds nothing changed in its rescan, so S5 acknowledged nothing, and the frame's entry sat in `ExternalChangeService` for its own ~600 ms settle — a play started inside that window held it, and every sync during play answered `stale` for a file the editor already ran. For a scene the same gap meant a sync answered ok before the scene was reloaded. |
| S6 | ~~Live components are not re-instantiated on re-registration (1.x parity, D7 kept).~~ Superseded by S7 (2026-10-10). | — |
| S7 | **Live components follow a changed script.** On re-registration `LiveComponentService` (`EC/services/scripting/LiveComponentService.ts`) replaces every component in an open scene whose type is registered with another class (runtime `replaceStaleComponents`: same id, `enabled`, slot; built like a load). Not an operation — no history entry, no dirty mark. The new instance's config = what a fresh load of the **baseline text** builds with the new class, plus the keys whose live value differs from the old baseline (unsaved edits); the baseline norm is re-derived with the new classes (as `rebaseOnPrefabChange` does for a prefab). A sync answers after the swap (`ProjectScriptLoaderService.componentsSettled`). History holds old instances: property and enabled undo/redo find the component by id; an undo/redo that brings an old instance back (removed component, deleted node) is followed by a replacement pass. During play nothing is swapped (registration itself waits for play to stop — the roots are queued, S13, and a restart applies them). ~~A type that no longer registers keeps its old instance.~~ Superseded by S12. | Replacing beats reloading: a reload clears the scene's undo history and loses a dirty scene's edits (or needs the merge); the swap keeps both. Without the baseline rebase a default the new class adds would read as an edit (dirty, flushed into the file); without the unsaved-edit overlay a dirty scene would lose its edit. A clean scene stays byte-for-byte what it was. |
| S10 | **Autoloads run in the runtime** (owner decision 2026-10-10, taken on the lead agent's recommendation while the owner is away; revertable by reverting `e768597` + `b138aac`). `pix3project.yaml` `autoloads: [{singleton, scriptPath, enabled}]` is read by one rule (`normalizeAutoloads`, class = the export named like the file, `autoloadComponentType`; `RT/core/autoloads.ts`) and built by `AutoloadHost` under `SceneRunner.setAutoloads(entries, registry)`: built before the session's first pre-roll tick (each singleton a component on its own `autoload:<singleton>` node under a hidden `__autoloads__` root, not in any scene graph, not rendered), `onStart` before any scene component's, ticked before the scene every frame, kept by a scene change (`runGraph` now stops the scene only — `stopScene`), `onDetach` after the scene's on `SceneRunner.stop()`, reverse order; an unresolved entry is a script error (`phase: 'attach'`) and is skipped. Scripts: `this.scene.getAutoload(name | Class)`. Hosts: the player (`runtimeAutoloads` in `virtual:pix3/scene-manifest`, dev and build, plus the project-scripts registry), the editor's play (`GamePlaySessionService` → the manifest's list + the editor `ScriptRegistry`; `AutoloadService` deleted, `ScriptExecutionService`'s autoload half gone), `pix3 smoke`, `createHeadlessGame({ autoloads })`. `pix3 validate`/`check`: `E_AUTOLOAD` (level 1 by text; level 2: the class is not a `Script`); a disabled entry is not checked. Live swap: nothing swaps during play and every play builds from the registry as it is, so an edited autoload runs its new class from the next play — no extra code. Kit: `project-files.md` recipe, the drift spec's "the player never reads autoloads" flipped. Build: the script is under `scripts/`, so the project-scripts glob bundles it and the scan reads it (and `pix3project.yaml`) like any source — `build.spec` checks the list and the class ship. | Before: only editor-core's `AutoloadService` built them, on a global root, and nothing ever started them (`ScriptExecutionService.start` has no caller); the player ignored the list, so a built game silently ran without them, and no script API reached one. A runtime host is the one way the editor's play and the build behave the same. Scene-scoped services stay scene-scoped (commands, tweens, physics an autoload registers are cleared with the scene; the network session is session-scoped like the autoloads) — documented, not special-cased. |
| S11 | **A module only bot policies import is applied during play** (closes the S4 debt). `ScriptGraph.policyOnlyModules()` (`VP/sync/script-graph.ts`): project modules reachable from `virtual:pix3/bot-policies` and not from `virtual:pix3/editor-scripts` in the client graph — none while the editor root is not in the graph. The barrier sends it in the `sync` request (`policyOnly`), the page passes it to `applySync`, `pendingDuringPlay` treats those paths like policies in both queues. An older plugin sends no list (the helper waits, as before); a helper the game's scripts also import still waits. | The plugin has the graph the page lacks. Computed whole on each sync (not per changed path) because the page's frame queue can hold the helper when the rescan found nothing (S9). |
| S12 | **A live component whose type disappeared is parked** (closes the S7 debt "keeps its old instance until the scene reloads"). `isStaleComponent` is also true for an unregistered type; `replaceStaleComponents` detaches it and pushes `{id, type, enabled, config}` (the live config) to `pendingComponents` — what `attachComponentDefinitions` does at load for a type it cannot resolve. | Match what a fresh load does: the save writes the same file, the re-derived baseline norm agrees (no dirty mark), `resolvePendingComponents` re-attaches it when the type returns. |
| S13 | **Script roots re-imported during play are queued for the stop, and `pix3_play restart` applies them before it starts** (2026-10-11; the review's HIGH finding). Before: `SyncApplyService.apply` threw away the roots the page had re-imported for a sync during play (`queueRoots` was reachable only from a `pix3:scripts` frame), the plugin broadcast that frame only from `handleHotUpdate` — which skips a change the barrier already propagated (the agent's sync usually gets there before chokidar) and which Vite 6+ calls for `update` only, never `create`/`delete` — and the restart reused the registry. So play → agent adds `scripts/Jumper.ts` + `user:Jumper` in the scene → sync `stale` → `restart` → sync **ok** with the scene reloaded and `user:Jumper` parked; the same for a deleted script (the old class stayed live) and for a modify synced before chokidar. Now: `SyncApplyService` queues `info.roots` on every sync during play (`ProjectScriptLoaderService.queueRoots`; the latest win); `applyQueuedRoots()` registers them synchronously — the bridge's restart calls it right after `game.stop`, waits for the live-component swap (`componentsSettled`), then `whenSettled` (the held scene reloads against the new registry, so its placed components resolve) and starts; the valtio subscription still covers a designer's stop. `ExternalChangeService.isSettled` no longer answers "settled" between the stop and its own asynchronous play-stop subscription (a `whenSettled` asked there resolved at once). Plugin: the `hotUpdate` hook (the environment API, Vite 7 and 8) replaces `handleHotUpdate`: a created or deleted globbed script re-runs the roots' globs and broadcasts `pix3:scripts {op}`; an update propagates as before; the work runs once on the client environment and every environment returns `[]`. Specs: `SyncApplyService.spec` (a stale sync during play queues the roots; an ok one too), `ProjectScriptLoaderService.spec` (`applyQueuedRoots` right after the stop, before the subscription), `debug-bridge.spec` (play as the agent → the sync handler gets roots with `Jumper` and a scene placing it → `restart` → `user:Jumper` registered, the hero's component an instance of it, the next sync ok), plugin `plugin.spec` (a script created, then deleted, outside a sync → `pix3:scripts` with `op`, the root globs it and then not) — all four fail at the previous HEAD. Browser: `scripts-e2e` 4a (below). | The barrier's promise (an ok sync = the editor runs the files on disk, A5: "after a restart the game runs the disk's files") was false for scripts while the records said it held. Queueing on the sync path is the only road that sees every case: the plugin cannot know whether the page kept the roots, and the watcher's frame is suppressed exactly when the sync propagated first. |
| S14 | **Scripts query groups through `this.scene`: `getNodesInGroup(group)` and `callGroup(group, method, ...args)` on `SceneService`** (owner decision 2026-10-11). Before: spec §6.19.2 promised them on `SceneManager`, which no script can reach — during play scripts run on the runner's clone and `this.scene` had no group query — and `SceneManager`'s copies had no caller; their per-scene index was fed by the editor's group / create / duplicate operations and read by nothing. Now: one implementation on `SceneService`, a depth-first walk of the running scene's roots (the same scope as `findNode`: not the autoloads' hidden root) reading each node's own `groups` at call time — no index, so `addToGroup`/`removeFromGroup`, spawns, frees and `changeScene` need no bookkeeping; `callGroup` snapshots the node list, calls the method on every component that has it, returns the count, warns once when the group has nodes and none has it. `SceneManager`'s index and its four group methods are removed and the editor operations no longer feed it (they still edit the node's `groups`). The build keeps it with no strip change: `SceneService` is always in a player and the methods add no import. Spec `SceneService.groups.spec.ts` (membership after load on the clone, add/remove/spawn/free, `changeScene`, a missing method); the kit's drift spec checks every `scene.*(` call the kit names against `SceneService`. | Groups are a script-facing feature (Godot's `get_tree().get_nodes_in_group` / `call_group`); the editor has no group query to serve. Reading `node.groups` is the one source of truth — an index beside it had to be kept in sync by every mutation path and nothing on the runtime side did. A tree walk per call is cheap at playable sizes. |
| S8 | **Bot-policy types come with the kit**, not from the editor: `packages/cli/kit-src/design/tests/bots/pix3-test-bot.d.ts` (global `Pix3TestBot` / `BotPolicy` / `BotNodeView` / `BotPoint` / `BotHit`, no import), held to `EC/services/game-test/game-bots.ts` by a `kit.spec.ts` drift test. The starter's `tsconfig.json` includes `design/tests`, so a policy written `{ … } satisfies BotPolicy` type-checks under `pix3 check` (a wrong call is `E_TYPE` at the policy). `GameBotHost.setDeclarationWriter`, `BOT_DTS_PATH` and `pix3-test-bot-dts.ts` are gone. `.pix3/tsconfig.check.json` (projects without a tsconfig of their own) still covers `scripts/` only. | The editor writes no project files (2.x); a package type export was the other option, but `@pix3/editor-core` ships only `dist/` (no declarations) and the runtime is game API, which the harness is not. The kit is already how a project gets agent-facing files with a drift guard, `pix3 new` installs it, and `--update` keeps it current without overwriting an edit (a 1.x editor-written copy counts as edited and is kept — the same globals). The pix3-types tsconfig is unchanged so a migrated 1.x project's untyped policies do not turn into new `E_TYPE`s. |
| S15 | **The barrier's page confirmation is asked again until it is current, and the roots are invalidated so Vite cannot hand a sync an older root** (2026-10-11). `ScriptGraph.hardInvalidateRoots` invalidates each root twice — as before, HMR-style, and again plain (`invalidateModule(mod, seen, undefined, false, false)`, Vite's monotonic clock). `SyncBarrier.run` step 4: when the tab answers `ok` but behind (`rev` < the rescan's `seq`, or a changed editor module's stamp not the disk sha) it re-invalidates the roots and asks again, after 50/100/200 ms, at most 4 asks, never past `timeoutMs`; a refusal (`!ok`) is never re-asked. The answer carries `attempts` when there was more than one; still behind → `stale_modules` with `paths` and `ackRev` as before. | Root cause of m3's 1-in-3–6 `stale_modules {paths: [], ackRev: 2, rev: 3}`: Vite 8's `transformRequest` dedupes a request on its URL without `?t=` and reuses the pending one unless `module.lastInvalidationTimestamp` is newer than it — and `invalidateModule(…, isHmr = true)` sets only `lastHMRTimestamp`. The second write's watcher `hotUpdate` broadcast `pix3:scripts`; the tab's re-import of the roots ran `load()` at the old `seq` (the file table had not rescanned yet); the sync's rescan bumped `seq` and invalidated the roots HMR-only; the sync's own re-import (`?t=` new) was handed that pending request — or, when it finished just after the invalidation, its result was cached as the root's `transformResult` (the same stale timestamp check). Stamps were current (the module itself was re-executed), only `__pix3Revision` lagged. The plain invalidation fixes the mechanism; the bounded re-ask is the barrier's own guarantee against any other late ack, and cannot hide a stale module (4 asks, ~350 ms, then the same `stale_modules`) or loop (attempt cap + deadline). |
